# 第三轮优化经验：先确认执行路径，再比较工作负载

[项目首页](../README.md) · [两档完整参数](../配置/第三轮W4A8配置.json) · [逐次数据](../数据/2026-11-06-第三轮实测.json)

2026-11-06 完成同机 A/B，2026-11-07 将 W4A8 + DSpark K5 standard 设为社区版默认服务。官方原始权重没有在本轮重跑。当前方案在已测单路中文/代码上较好；K3 在并发及单路英文上较好，不把“最优”解释为所有工作负载的全局最优。

## 一、把建议转换为可验证的假设

最初的分析正确指出冷预填充、小批量解码效率和并发调度值得优先验证。我们先在同权重、同镜像、同四卡上建立基线，再逐步测试解码开关、4096/8192预填充块、调度、W4A8路径和K3/K4/K5。最后恢复原配置做前后对照，再单独上线选定配置。

公开成绩可以提供目标范围，但不能代替本机基线。旧209 tok/s来自不同提示词/批次，旧官方与社区版表也不是本轮A/B基线。此次基线单路中文/代码/英文为228.54/255.72/219.80 tok/s；优化后的百分比均相对这一基线计算。

## 二、环境变量设为1，不代表内核实际被调用

原运行配置强制 `VLLM_B12X_MOE_FP4_FORCE_A16=1`，对应 `B12X_MXFP4_BF16`。即使设置 `VLLM_MOET_B12X_MOE_FUSED=1` 与 `VLLM_MOET_B12X_MOE_PREFILL_FAST=1`，相关W4A8路径仍被绕开。A16组的提升不能归功于没有进入的融合内核。

切换W4A8时先运行镜像内算子校验，175/175组结果、图重放及服务路径检查通过，再加载完整模型；随后核对 `B12X_MXFP4_MXFP8`、SP和fast-prefill的实际激活日志，并做模型级质量检查。算子相对同精度参考实现一致，不等于W4A8与A16整个模型逐字节等价。

`INDEXER_TP_SHARD_MIN_ROWS`属于上游启动包装脚本的变量。直接启动vLLM时，需要把 `indexer_tp_shard_min_rows=2048` 放进 `--attention-config`。同理，内核已编译、镜像含有代码、参数被接受、实际走入该路径，是四种不同证据。

## 三、预填充是本轮最大的延迟收益

| 配置组合 | 1M冷TTFT中位数 |
|---|---:|
| 原A16、batch1024 | 222.55秒 |
| A16、batch4096、SP/indexer等组合 | 79.88秒 |
| A16、batch8192、SP/indexer等组合 | 63.34秒 |
| W4A8融合、batch8192、K3 | 55.40秒 |
| W4A8融合、batch8192、K5 | 55.33秒 |

每个长度两次独立冷样本，输入首部使用唯一盐值，核对缓存命中增量为0。固定前缀的长请求可能几乎不重算，不能拿它冒充百万冷预填充。首次形状编译可能使第一轮较慢，两轮均保留，不只挑较快一轮。

这是一组组合参数的A/B结果，没有为每个预填充开关独立分配因果贡献。1M冷测试使用短检索答案，不是本轮重新测了1M输入后持续输出1024 token的速度；旧长输出测试保留在历史数据中。

## 四、K值必须按任务选择

K表示每轮草稿token数，不是并发请求数。W4A8下，K5单路中文/代码为269.24/327.75 tok/s，K3为240.54/272.39；单路英文则K3的253.79高于K5的243.15。

八路中文/代码/英文聚合吞吐，K3为810.04/850.97/733.77，K5为712.34/800.10/678.77 tok/s。四路下K3也整体更好。增加草稿长度会增加草稿与验证开销，接受更多token并不保证最终更快。

K4单路中文/代码/英文约252/290/241，未形成统一优势。K5 block约267/322/242，与standard接近而略低，并发也没有稳定优势，因此保留standard。没有测试运行时自动切K，现有默认是固定K5。

## 五、首字等待和完整请求耗时必须同时报告

在128K冷请求开始1秒后加入一个短输入、1024输出预算的请求：原配置短请求约26.5秒出首字、30.8秒完成；W4A8 K5公平调度约0.67秒出首字、10.4秒完成。

公平调度使用 `--long-prefill-token-threshold 2048 --long-prefill-token-threshold-adaptive`。保留原计算精度的对照中，公平调度使短请求更早出首字，但生成期间要与长预填充分享GPU，因此完整耗时未必比不公平分块更短。这个场景测试的是新请求加入，不是已有解码流被长请求打断。

八个短请求能并行，不代表八个独立1M上下文能同时驻留。KV保持6 GiB/GPU；没有用seqs=8来宣称满上下文并发容量提升到8路。

## 六、质量差异要保留失败并重复基线

基线GSM8K chat为197/200。decode-A16、关闭目标LM-head量化但保留BMM的组、原精度公平调度组及W4A8 K4均出现过196/200。不能直接把这一题差异全归因于新量化：case1303有1024 token截断，原配置重复5次也出现4/5；case675涉及数量关系解释，实验后原配置重复为3/5。

这些诊断不改变正式分数。没有删题、扩大失败题的预算后再冒充原成绩，也没有把一次高分当作普遍质量无损。K3、K5和K5-block的W4A8固定GSM200均197/200，同错题；混合chat29/30、low30/30，应用10/10、图像2/2。

本轮未重新测试GSM8K low。历史官方195/200、社区192/200的low结果依然保留；不能拿本轮chat197/200覆盖这条不利历史结果。

## 七、测量与调度经验

- 冻结提示词、预算、temperature、seed、评分题号、权重revision和镜像内容ID。固定seed仍可能产生不同输出；速度包含接受长度变化，不能全部解释成纯内核加速。
- 单路解码用 `(completion_tokens-1)/(最后输出时间-首次输出时间)`；投机流的一块可能有多个token，不能按SSE块数数token。
- 并发聚合用该批全部输出token/整批墙钟时间，含等待与排队；每路解码中位数不能简单乘并发数得到聚合吞吐。
- 草稿计数/请求墙钟秒不是纯CUDA步频。采样P99也不是线上P99。
- 检查运行/排队请求与GPU占用，取得切换锁，所有候选串行占卡，记录容器身份和镜像，不重叠启动两份模型。
- 每次完整加载与预热约数分钟，是数小时实验的大部分固定开销之一。先做源码路径和算子预检，再跑完整模型，避免无效重启。
- 测试脚本不要命名为 `queue.py`、`json.py` 等标准库模块名。本轮早期的queue重名使线程池无法正常启动；改名后恢复，未把未启动的测速当作有效样本。
- 审计阶段共11条配置/前后对照记录、1353次测速请求，提示词哈希与题号集合一致，无请求计数异常；前后原配置单路中位最大变化0.50%，八路聚合2.47%。测试不是随机交错进行，仍保留这一方法限制。

## 八、上线不止是修改Docker参数

必须同时更新服务环境、模型切换保存的profile、容器命令清单及其指纹。启动器原先写死A16校验，需要改为与已验证清单一致性校验；否则候选可能被拒绝或退回旧路径。保留原A16/K3配置作为故障恢复，并明确区分Docker正常服务和native fallback。

本次上线等请求空闲后执行，备份原文件，失败自动恢复；上线后核对实际Docker参数、权重挂载、镜像、模型别名、真实输出，以及应用/图像检查。更新开机使用的配置与模型切换profile，不能只让临时容器变快。上线完成后又做每类3次速度检查，结果与5次A/B表分开保存。

## 九、仍未回答的问题

没有测新镜像、TensorRT-LLM/SGLang、TP8、FP4 KV、主机/磁盘KV offload、长期线上P99、最高思考档速度或完整研究代理工作流。已有成果不证明这些方案无用。也没有把GPU功耗采样峰值误写成300W功率上限；现有限制仍为600W，没有为本轮提速调整功率上限。

后续先根据真实并发、输入长度、缓存命中和任务类型选择负载，再考虑扩容或进一步内核组合。当前公开数据足以复算本轮统计，但不能替代在另一台主机上的重新验证。
